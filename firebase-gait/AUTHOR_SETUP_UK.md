# Підключення модуля аналізу ходьби до Firebase автора

Модуль уже містить Android-інтерфейс, локальний аналіз, збереження сеансів,
синхронізацію числових результатів і доступ лікаря за запрошенням. Для підключення
потрібні конфігурація Android-застосунку з Firebase автора та відповідні правила
Cloud Firestore. Окремий сервер обробки відео для цього модуля не потрібний.

Ця інтеграція працює на Android. Наявні авторські REST-функції реабілітації та інші
API залишаються окремими: їхні адреси, DTO, маршрути й авторизацію потрібно
зберегти під час об'єднання коду. Firebase цього модуля не замінює Rehab REST API.

## 1. Вибрати Firebase-проєкт і конфігурацію Android

1. Відкрити **потрібний проєкт автора** у Firebase Console. Authentication і
   Firestore модуля мають належати цьому самому проєкту.
2. Перевірити зареєстрований Android-застосунок із package name
   **`com.example.coverdesign`**. Це поточний `applicationId` у
   `androidApp/build.gradle.kts`; регістр має значення.
3. Завантажити його `google-services.json` і покласти файл саме в
   **`androidApp/google-services.json`**, без суфіксів на кшталт `(1)`.
4. Виконати Gradle Sync і зібрати APK заново. Заміна JSON не змінює вже зібраний APK.

Файл `google-services.json` уже виключений із Git. Він містить клієнтські
ідентифікатори Firebase; це не Service Account. Приватний ключ або Admin SDK JSON
для Android-застосунку не потрібний і в APK не додається. Клієнтські права доступу
визначають Firebase Auth і Firestore Rules, а не сам конфігураційний файл.

Зберегти авторський ключ підпису застосунку. Для оновлення вже встановленого
застосунку потрібні сумісний підпис і більший `versionCode`. Не підміняти release
ключ випадковим debug-ключем. [Офіційне підключення Android до Firebase](https://firebase.google.com/docs/android/setup).

## 2. Увімкнути потрібний спосіб входу

Для найпростішого першого тесту достатньо **Authentication → Sign-in method →
Email/Password → Enable**. Користувачі повинні входити через Firebase Auth того
проєкту, у якому зберігаються звіти. [Налаштування Email/Password](https://firebase.google.com/docs/auth/android/password-auth).

Якщо потрібна кнопка Google:

- Увімкнути Google як провайдера входу.
- Додати SHA-1 **сертифіката, яким підписаний фактичний APK**. Для локальних debug
  збірок і авторського release-підпису це зазвичай різні сертифікати. Якщо збірка
  розповсюджується через Google Play, врахувати сертифікат Play App Signing.
- Після налаштування Google/SHA повторно завантажити `google-services.json`.
- Зберегти читання згенерованого ресурсу `default_web_client_id`: він має містити
  OAuth **Web client ID**, а не Android client ID. У поточному коді ресурс читає
  `shared/.../di/AndroidModule.kt`; вручну вписувати чужий ID не потрібно.

Без цього ресурсу код показує, що Google-вхід не налаштований, і пропонує
Email/Password. Відбитки власної збірки можна отримати командою
`./gradlew :androidApp:signingReport`. [Офіційне налаштування Google-входу](https://firebase.google.com/docs/auth/android/google-signin).

## 3. Підключити правильну базу Firestore

Код використовує стандартну базу **Cloud Firestore `(default)`**, оскільки викликає
`FirebaseFirestore.getInstance()`. Окрема іменована база автоматично не обирається.
Якщо Firestore у проєкті ще немає, створити базу в потрібному регіоні із закритими
початковими правилами, а потім опублікувати перевірені правила нижче.
[Бази Firestore](https://firebase.google.com/docs/firestore/manage-databases).

### Якщо в автора вже є Firestore і правила

1. Зберегти точну копію поточних опублікованих правил.
2. Відкрити `firebase-gait/firestore.gait.rules`. Усередину існуючого блоку
   `match /databases/{database}/documents` перенести всі функції `gait*` та три
   верхні блоки `gaitDoctorCodes`, `gaitShares`, `gaitReports`.
3. Разом із `gaitReports` перенести вкладений блок **`details/{chunkId}`** і функції
   перевірки `detailManifest`/частин. Правил лише для компактних кутів недостатньо
   для повного звіту лікаря та графіків сеансу.
4. Зберегти `rules_version = '2'`; не дублювати зовнішні `service`/`documents` блоки.
   Авторські правила `users`, замовлень, конфігурацій та інших функцій не замінювати.
5. Перевірити дозволи, що перетинаються. Загальний
   `match /{document=**} { allow read, write: if ...; }` може відкрити медичні дані,
   навіть коли додані gait-правила обмежувальні: достатньо одного дозволяючого
   збігу. Звузити такий загальний дозвіл, зберігши потрібні авторські сценарії.
6. Перевірити злиті правила й звичайні авторські функції, потім опублікувати їх
   саме в проєкті автора через його звичний процес випуску.

**Не замінювати правила існуючого авторського проєкту файлом
`firestore.dev.rules` або ізольованим `firestore.gait.rules` цілком.** Перший містить
лише мінімальні базові дозволи, другий не містить авторських дозволів узагалі.
[Як працюють правила, що перетинаються](https://firebase.google.com/docs/firestore/security/rules-structure#overlapping_match_statements).

### Якщо це нова порожня демонстраційна база

Можна використати повний `firebase-gait/firestore.dev.rules`. Він зібраний із
gait-фрагмента та `firestore.dev-base.rules.inc` і містить власний профіль,
власні `configs` і `orders`. Профіль створюється з роллю `PATIENT` або `DOCTOR`;
UID, роль і дата створення після цього незмінні. Цей мінімальний варіант не
замінює виробничі права автора, сценарії `TECHNICIAN` або його REST-сервіс.

## 4. Профілі користувачів і доступ лікаря

Профіль має лежати в `users/{FirebaseAuthUid}`. Поточний контракт використовує
`uid`, `email`, `displayName`, `phone`, `role`, `createdAt` — ціле число мілісекунд
Unix; `hasInsoles` може бути булевим додатковим полем. Ролі для аналізу:
**`PATIENT`** і **`DOCTOR`**, у верхньому регістрі.

Якщо в авторському проєкті вже є користувачі Auth, перевірити їхні профілі й ролі
до тестового входу: сам запис у Firebase Authentication не створює потрібний
документ Firestore. Вхід у застосунку перевіряє профіль. Автоматичне створення
відсутнього `PATIENT` профілю для вже відкритих тестових сеансів не є міграцією
всіх авторських користувачів. Існуючу роль код синхронізації не перезаписує.

Для перевірки найпростіше зареєструвати через застосунок два окремі облікові
записи після налаштування правил: пацієнта і лікаря.

| Шлях | Призначення |
| --- | --- |
| `gaitDoctorCodes/{code}` | Випадковий код запрошення конкретного лікаря; список кодів закритий. |
| `gaitShares/{patientUid}` | Явний дозвіл пацієнта одному лікарю. |
| `gaitReports/{patientUid}/sessions/{sessionId}` | Підсумки кутів, контекст вимірювання та якість; schema 1. |
| `gaitReports/{patientUid}/sessions/{sessionId}/details/{0..63}` | Частини повного числового сеансу, описані необов'язковим `detailManifest`. |

Лікар отримує код у своєму кабінеті. Пацієнт вводить його в **Gait → Results &
doctor access** і надає доступ. Роль `DOCTOR` сама по собі не відкриває жодного
пацієнта та не означає перевіреної медичної кваліфікації. Після відкликання доступу
лікар втрачає наступні серверні читання, а екран прибирає його дані.

Повний числовий сеанс містить часові ряди кутів і параметри профілю, з якими його
було записано, щоб лікар відкривав той самий звіт. Відео, фотографії, координати
суглобів і кольорові калібрувальні знімки цей транспорт не передає. Старі компактні
документи залишаються валідними; повні графіки з'являться після повторної
синхронізації з телефону, де ще є первинний локальний числовий сеанс.

## 5. Індекси, Storage та інші служби

За звичайного автоматичного індексування додаткові складені індекси для поточних
запитів не потрібні: список пацієнтів фільтрується за `doctorUid` і `active`,
деталі — за `index`, сортування звітів виконується в клієнті. Не вимикати потрібні
індекси цих полів. Якщо автор змінить запити або вже має винятки індексування,
перевірити вимоги заново. [Індекси та об'єднання equality-індексів](https://firebase.google.com/docs/firestore/query-data/index-overview#use_index_merging).

Для числових gait-звітів достатньо Auth + Firestore. Новий Storage bucket,
Storage Rules, Cloud Functions чи сервер обробки не потрібні. Зберегти наявне
налаштування Storage для авторських фото/текстур і окремого інструмента запису
відео; той інструмент не є синхронізацією gait-звітів.

## 6. Перевірка до передавання користувачам

Із кореня Android-проєкту:

```sh
./gradlew :androidApp:assembleDebug
```

Для цієї перевірки не використовувати `-PcompileWithoutFirebase=true`: цей
прапорець лише допомагає перевірити компіляцію без Firebase-конфігурації.

Локальні перевірки правил не потребують входу у Firebase CLI й не публікують
нічого в авторський проєкт:

```sh
cd firebase-gait
npm ci
npm test
npm run test:dev
```

Тести запускають Firestore емулятор із проєктом `demo-coverdesign-gait`.
`npm test` перевіряє gait-фрагмент, `test:dev` — додатково мінімальні базові права.
Для власних злитих правил також потрібна перевірка саме злитого файла; проходження
наших початкових правил не доводить безпечність авторського злиття.

Для окремої перевірки реального Android-транспорту запустити в одному терміналі
`npm run emulators:android`. В іншому, із кореня проєкту, за відкритого Android
Emulator виконати:

```sh
./gradlew :androidApp:connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=com.example.coverdesign.gait.GaitCloudRepositoryTest \
  -Pandroid.testInstrumentationRunnerArguments.gaitCloudEmulator=true
```

Цей клас створює окремі тестові FirebaseApp у `demo-coverdesign-gait`, підключається
до `10.0.2.2:9098` / `10.0.2.2:8185`; спеціальний `GaitTestRunner` не запускає
звичайний хмарний завантажувач у цьому режимі. Після тесту зупинити локальні
емулятори Firebase через Ctrl+C. Не запускати другий сервер на тих самих портах.

Нарешті перевірити авторський проєкт на двох тестових облікових записах: зберегти
сеанс із вимірюваннями, дочекатися підтвердження синхронізації, надати доступ за
кодом, відкрити той самий сеанс і графіки в лікаря, відкликати доступ. Окремо
перевірити наявні замовлення, конфігурації та REST-реабілітацію після злиття.

## 7. Що не переносить заміна конфігурації

Заміна `google-services.json` **не переносить** користувачів Firebase Auth,
стару хмарну базу, запрошення або дозволи між проєктами. Однакова адреса email
в іншому проєкті не гарантує того самого Auth UID. Історія не завантажується
автоматично в локальне сховище нового телефону з повних хмарних звітів.

Локальна gait-історія зараз розділена за **Auth UID**, а не за Firebase project ID.
Підтвердження синхронізації вже розділені за `projectId:UID`. Завантажувач стартує
із застосунком і синхронізує збережені сеанси поточного UID. Тому:

- за іншого UID стара локальна історія не відобразиться;
- якщо UID збережено під час переходу в інший проєкт, локальні сеанси можуть
  автоматично завантажитися в новий проєкт повторно;
- перенесення користувачів, історії й дозволів потребує окремого плану міграції.

Перше підключення автора перевіряти на **чистому емуляторі або окремій тестовій
установці**, без реальної збереженої історії. Існуючі дані та підпис авторського
застосунку зберегти. Конфігурація нового проєкту — це підключення, а не міграція.
