# Передача модуля аналізу ходьби автору CoverDesign

Підготовлено окрему гілку `feature/gait-analysis` на актуальній `stable/v1`
автора: `6f574efe769e80017a6c79864c78978d0e97a430`.
Це інтеграційна версія Android 1.3.1 (versionCode 14).

## Що передається

- Аналіз наживо без маркерів і з маркерами; імпорт відео з маркерами.
- Вибір кольорів лише зі знімка маркерів на тілі, інструкції, перевірки положення
  телефона, короткі проходи, голосові підказки, пауза й часткові результати.
- Локальна історія, показники та денні графіки пацієнта.
- Firebase: повні числові сеанси, підключення лікаря за кодом, відкликання доступу,
  однаковий звіт пацієнта й лікаря з графіками всередині сеансу.
- Правила доступу, автоматичні перевірки, документація.

Обчислення виконуються на Android. Повний числовий звіт включає ряди кутів,
параметри профілю й сеансу; фото та відео цей модуль у Firebase не передає.
iOS і Desktop для нового модуля не реалізовувалися.

## Як прийняти зміни через GitHub

Якщо відправник має право створювати гілки у репозиторії:

```sh
git push -u origin feature/gait-analysis
```

Після цього створити Pull Request **з `feature/gait-analysis` у `stable/v1`**.
Автор переглядає зміни, підключає свій Firebase, перевіряє сценарії й зливає PR.
Якщо права запису немає, використати fork + Pull Request або Git bundle нижче.
Підготовка локальної гілки сама не публікує код на GitHub.

## Як передати без доступу до GitHub: Git bundle

Разом із цим документом передати `CoverDesign-gait-integration.bundle`.
Він містить коміт інтеграції та нові файли модуля, але не особисту конфігурацію,
збірки, залежності npm чи приватні відео. Це не ZIP робочого каталогу.

Автор виконує у власному клоні з чистим робочим каталогом:

```sh
git fetch origin
git bundle verify /шлях/до/CoverDesign-gait-integration.bundle
git fetch /шлях/до/CoverDesign-gait-integration.bundle feature/gait-analysis:feature/gait-analysis
git switch feature/gait-analysis
```

Bundle вимагає наявності базового коміту `6f574efe…` у клоні автора; `git fetch origin`
отримує його зі спільної історії. Перед переглядом порівняти з поточною гілкою:

```sh
git diff origin/stable/v1...feature/gait-analysis --stat
```

Після перевірки автор зливає гілку своїм звичайним способом. Якщо автор додав нові
коміти після `6f574efe…`, спочатку узгодити їх із feature-гілкою та повторити перевірки.
Нічого примусово не перезаписувати у `stable/v1`.

## Підключення Firebase автора

Повна інструкція: [firebase-gait/AUTHOR_SETUP_UK.md](firebase-gait/AUTHOR_SETUP_UK.md).
Короткий порядок:

1. Використати Firebase-проєкт автора для Auth і default Cloud Firestore.
2. Зареєструвати Android-застосунок `com.example.coverdesign`, увімкнути потрібні
   способи входу та додати SHA ключа, яким автор підписує свою збірку.
3. Покласти його актуальний `google-services.json` у `androidApp/` локально.
4. Додати gait-функції та правила з `firestore.gait.rules` до чинних правил автора,
   зберігши його правила користувачів, замовлень та конфігурацій. Потрібні також
   вкладені `sessions/{id}/details/{index}` для повних графіків.
5. Перевірити об’єднані правила й опублікувати їх у Firebase автора.
6. Зібрати застосунок та перевірити два тестові акаунти: PATIENT і DOCTOR.

Просто замінити JSON недостатньо: конфігурація не переносить користувачів, дані,
запрошення або правила доступу між Firebase-проєктами. Для першого запуску з
проєктом автора використати чистий емулятор/окреме тестове встановлення. У наявній
інсталяції локальна історія прив’язана до UID; однаковий UID в іншому Firebase може
спричинити повторне завантаження старих локальних сеансів до нового проєкту.
Тестова база `coverdesign-dev` залишається окремою; доступ до неї не потрібен для
роботи коду у Firebase автора. Ключ сервісного акаунта в Android-застосунок не потрібен.

## Узгодження з новими змінами автора

Інтеграція враховує нові авторські коміти `67096ee`, `b173963`, `6f574ef`.
Збережено авторські сервіси/моделі Rehab REST, його запис та відправку відео,
оновлення Home після завершення серверної сесії, актуальні замовлення й 3D-preview.
На Home серверний реабілітаційний звіт і локальні gait-вимірювання мають окремі блоки.
Файл нового авторського списку пацієнтів збережений; вкладки лікаря використовують
підтверджені зв’язки Firebase, оскільки авторський список поки містить TODO отримання
пацієнтів. Старі демонстраційні рекомендації не видаються за звіт gait-сеансу.

Rehab REST та gait Firebase — два окремі контури. Заміна Firebase-конфігурації не
налаштовує REST-сервер. Його адреса залишається в
`shared/src/commonMain/kotlin/com/example/coverdesign/data/remote/client/ApiConstants.kt`;
на поточній upstream-гілці це адреса локального сервера для Android-емулятора.
Автор має налаштувати свою адресу для реального телефона та чинний сервер.

## Перевірки перед прийняттям

```sh
./gradlew :androidApp:assembleDebug :androidApp:assembleDebugAndroidTest :androidApp:testDebugUnitTest :shared:testAndroidHostTest
```

Для локальних правил Firebase:

```sh
cd firebase-gait
npm ci
npm test
npm run test:dev
```

Останні два сценарії працюють з локальними емуляторами; вони не публікують правила.
Перед злиттям перевірити також авторські замовлення, 3D, запис відео/REST і:

- PATIENT: повний сеанс → історія → графіки → синхронізація без дублювання;
- DOCTOR: код → підключений пацієнт → Open session report → ті самі графіки;
- відкликання доступу, видалення сеансу та повторна синхронізація після втрати мережі;
- ролі/акаунти не змішують чужі результати.

Стан останньої інтеграційної перевірки та відомі обмеження наведено у
`INTEGRATION_VERIFICATION.md`. Автоматичні перевірки не підтверджують клінічну
точність вимірювань. Модуль не встановлює діагноз і не має перевірених меж норми.
